Golden Configuration

A golden config is the approved, security-hardened baseline for a specific device class (e.g., "all branch routers"). It is version-controlled and serves as the reference state. IaC tools (Ansible, Terraform, NAPALM) continuously compare running configs against the golden config and alert on or remediate configuration drift — unauthorized or accidental changes.

System Life Cycle Management

Every device and platform moves through the same arc: procure → deploy → maintain → retire. The exam cares about the two ends of that arc — the vendor dates that end support, and the process for taking a system out of service cleanly.

Software Management

"Keeping it patched" is three distinct managed artefacts on the exam, and they are updated on different schedules by different teams:

ArtefactWhat it updatesOperational notes
Patches & Bug FixesTargeted corrections to a specific defect or vulnerability in existing softwareSmallest and most frequent. Security patches are the ones with a clock on them — patch Tuesday cycles, emergency out-of-band releases for actively exploited flaws
Operating System UpdatesThe device or host OS as a whole — new features, cumulative fixes, version upgradesLarger blast radius than a patch; typically needs a maintenance window and a rollback plan. A major version jump can drop support for older hardware
Firmware UpdatesThe low-level code burned into the hardware itself — switch/router IOS images, AP firmware, NIC and BMC firmwareThe riskiest of the three: a failed firmware flash can brick the device. Always verify the image checksum and keep a known-good image reachable for recovery

Decommissioning

Decommissioning is a process, not just the document that records it. Skipping steps is how stale DNS entries and undocumented open ports outlive the hardware that justified them:

  • Archive the configuration — export the final running config before power-off; it is the only record of how the device was actually set up.
  • Sanitize the data — wipe or physically destroy any storage. Certificates and cached credentials live on network gear too, not just servers.
  • Reclaim the addressing — release the IP in IPAM, remove DHCP reservations, and delete stale DNS A and PTR records.
  • Clean up dependencies — remove monitoring checks, firewall rules, ACL entries, and routing/VLAN references that pointed at the device.
  • Dispose of the asset — update the asset inventory and record the disposal chain of custody.

Change Management Process

The change management document is listed above; the objective also wants the request process itself. A change request (also called a service request) moves through named stages, and every stage is a place the exam can stop and ask "what happens here?"

StageWhat happensWhy it matters
1. RequestChange is submitted and tracked with a ticket ID, describing scope, affected systems, and reasonCreates the audit trail — every change is traceable to a requester
2. ApprovalReviewed by a change advisory board or manager; risk and impact are assessed and a maintenance window is scheduledThe gate. An unapproved change is an incident waiting to happen
3. ImplementationChange is applied during the approved window, following the documented stepsConfiguration is backed up before the change so there is something to roll back to
4. VerificationTest that the change did what it was meant to do and broke nothing elseIf verification fails, the rollback plan executes — restore the pre-change config
5. DocumentationUpdate diagrams, asset inventory, baselines, and the knowledge baseThe step most often skipped, and the reason documentation drifts from reality

Configuration Management

Three configurations exist for any managed device at the same time. Telling them apart is the exam point:

ConfigurationWhat it isWhen you use it
Production ConfigurationThe live running config on the device right now — including any change made since the last backupThis is the state that is actually forwarding traffic. It may legitimately differ from both of the others
Backup ConfigurationAn archived copy of this specific device's config, taken at a point in timeRestoring after a failed change or replacing failed hardware — it returns one device to how it was
Baseline / Golden ConfigurationThe approved standard for an entire device class, not one deviceProvisioning new devices and auditing existing ones. Deviation from it is configuration drift — see the callout above
Backup Config vs. Golden Config

Both are "a saved config," which is exactly why they get confused. A backup config is per-device and historical — it answers "how was this switch set up on Tuesday?" A golden config is per-class and prescriptive — it answers "how should every branch switch be set up?" Restoring a backup returns one device to its own past state; restoring from golden brings a device into line with the standard, discarding whatever drift it had accumulated.

⚠ Exam Traps
  • A baseline is taken before a problem occurs — it represents "normal." You compare current metrics against it.
  • Change management includes a rollback plan — what to do if the change causes issues.
  • IPAM ≠ DHCP — DHCP dynamically assigns addresses; IPAM documents and manages the entire address space across all subnets.
  • EOL ≠ EOS — EOL = no longer sold; EOS = no longer patched (the security-critical date). A device can be EOL but still supported.
  • Golden configuration = the approved baseline. Configuration drift = deviation from it.
  • Backup config ≠ golden config — a backup restores one device to its own earlier state; the golden config is the standard for a whole device class. "Restore from backup" and "reapply the golden config" are different answers.
  • BCP ≠ DR — business continuity keeps the business running (including non-IT workarounds); disaster recovery restores the IT systems. DR sits inside BCP, not beside it.
  • MOU ≠ SLA — an MOU is non-binding intent; an SLA is contractual with measurable targets and penalties.
  • Firmware is the update that can brick the device — it is the riskiest of patches / OS updates / firmware, not the most routine.
  • Containment (isolate the host) comes before eradication — never skip directly to reimaging without containing first.
