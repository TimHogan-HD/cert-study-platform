Objective 3.5

3.5 Network Access & Management Methods

VPN Types

TypeDescriptionUse Case
Site-to-Site VPN Permanent tunnel between two network sites (typically router-to-router). All traffic between sites traverses encrypted tunnel. Branch office to HQ connectivity; replaces dedicated WAN circuits.
Client-to-Site (Remote Access VPN) Individual user connects to the corporate network over the internet — with an installed client, or clientless through a browser. See the detail below for split vs full tunnel. Remote workers, WFH employees.
SSL/TLS VPN Uses HTTPS (port 443) — traverses firewalls easily. Browser-based or thin client. (Also called SSTP, OpenVPN). Clientless access to web apps, easy deployment through NAT/firewalls.
IPsec VPN IP Security — encrypts/authenticates at Layer 3. Uses IKE for key exchange. Site-to-site and client-to-site. Most common enterprise VPN protocol.

Client-to-Site VPN Detail

Client-Based vs. Clientless

AspectClient-Based VPNClientless VPN
What the user runs A dedicated VPN client installed on the device (AnyConnect, GlobalProtect, native IPsec/IKEv2 client) Nothing — just a browser. The TLS session to the VPN portal is the tunnel
What the user reaches The network. The device gets an IP on the corporate network and can reach any permitted resource and protocol Only what the portal publishes — typically web applications, plus file shares or RDP proxied through the browser
Deployment Software must be installed, updated, and supported on every endpoint Nothing to deploy — works from an unmanaged or third-party machine
Typical use Managed corporate laptops needing full access Contractors, kiosks, or personal devices needing access to a handful of internal web apps

Clientless VPNs run over HTTPS on port 443, which is why they traverse restrictive firewalls and hotel or captive-portal networks that block IPsec.

Split Tunnel vs. Full Tunnel

This applies to client-based VPNs and decides one thing: which of the user's traffic is forced through the tunnel.

AspectFull TunnelSplit Tunnel
Traffic through the tunnel All traffic, including internet browsing, which exits via the corporate network Only traffic destined for corporate subnets. Internet traffic goes direct from the user's local connection
Security Stronger — every packet passes corporate filtering, inspection, and logging, so policy applies off-site exactly as on-site Weaker — internet traffic bypasses corporate inspection entirely. A compromised host can reach the internet and the corporate network at once, bridging the two
Performance and cost Concentrates all remote traffic on the VPN concentrator and corporate internet link — the bottleneck at scale. Adds latency to cloud services by backhauling them Far less load on the concentrator; cloud and streaming traffic takes the direct path, so it feels faster to the user
Typical use Regulated environments and any case where full visibility of user traffic is required Large remote workforces using SaaS heavily, where backhauling video calls would saturate the link
The Trade-off in One Line

Full tunnel buys inspection at the cost of bandwidth; split tunnel buys performance at the cost of visibility. Exam scenarios usually signal which is wanted: mentions of compliance, monitoring, content filtering, or inspecting all user traffic point to full tunnel. Mentions of VPN concentrator saturation, slow video calls, or backhauling cloud traffic point to split tunnel.

IPsec Components

ComponentFunction
AH (Authentication Header)Provides authentication and integrity only. NO encryption. Protocol number 51. Not widely used alone.
ESP (Encapsulating Security Payload)Provides authentication, integrity, AND encryption. Protocol number 50. Most common IPsec component.
IKE (Internet Key Exchange)Negotiates security associations (SAs) and establishes shared keys. IKEv1 (older) and IKEv2 (current, more efficient). Uses UDP port 500 (phase 1) and UDP 4500 (NAT traversal).
Tunnel ModeEntire IP packet is encrypted and encapsulated in new IP packet. Used for site-to-site VPNs.
Transport ModeOnly the payload is encrypted; original IP header preserved. Used for host-to-host encryption (e.g., L2TP over IPsec).

EAP and EAPoL — What 802.1X Actually Carries

EAP is not an authentication method. It is a framework — an envelope that carries whatever method the two ends agree on, which is why 802.1X can authenticate a certificate, a password, or a token without the switch understanding any of them. The methods themselves are the EAP types: EAP-TLS (certificates on both sides — strongest, and the reason it needs a PKI), PEAP (a TLS tunnel from the server's certificate alone, with a password authenticated inside it), and EAP-TTLS (similar tunnelling, broader legacy method support). "We use EAP" says nothing about how strong the authentication is; the type does.

EAPoL is how those EAP messages travel across the wired or wireless LAN between supplicant and authenticator, before the supplicant has an IP address at all. The authenticator then unwraps each EAP message and re-sends it to the RADIUS server inside a RADIUS packet — so EAPoL runs supplicant → authenticator, and RADIUS runs authenticator → authentication server. The EAP conversation is end-to-end between supplicant and server; only its transport changes in the middle.

Not in official objectives Objective 3.5 lists VPN types, remote access protocols, and access management methods. EAP and EAPoL are not enumerated in any bullet, but both appear in the official N10-009 acronym list, and 802.1X — which is enumerated under 4.1 — cannot be explained without them.

⚠ Exam Traps
  • RADIUS = UDP | TACACS+ = TCP. This is the #1 most-tested RADIUS/TACACS+ fact.
  • TACACS+ encrypts the entire packet. RADIUS encrypts only the password.
  • TACACS+ is for device (router/switch) management. RADIUS is for network access (Wi-Fi, VPN).
  • IPsec ESP provides encryption. IPsec AH does NOT encrypt — it only authenticates.
  • 802.1X supplicant = client. Authenticator = switch/WAP. Authentication server = RADIUS.
  • Split vs full tunnel is a trade-off, not a right answer. Full tunnel inspects everything but concentrates all remote traffic on the VPN concentrator; split tunnel is faster and lighter but leaves internet traffic uninspected.
  • Clientless ≠ split tunnel. Clientless is about whether software is installed (browser/TLS portal); split vs full is about which traffic is routed through the tunnel.

⚠ Access Methods Exam Traps
  • Jump box = bastion host — same concept, different names. Admins never SSH directly to production devices.
  • OOB = separate path that survives production failure. If the question mentions "can't reach the device over the network," the answer is OOB or console.
  • Console port = ultimate OOB — it works even when the OS is partially broken or the NIC has failed.
  • Telnet (23) = unencrypted, never use. SSH (22) = encrypted, required for production.
  • NETCONF uses port 830 TCP; RESTCONF uses 443 (HTTPS).
Quick Recall — 3.5
  • RADIUS: UDP 1812/1813, encrypts only password, combines Auth+Authz
  • TACACS+: TCP 49, full packet encryption, separates AAA functions
  • IPsec: AH=auth only | ESP=auth+encryption | IKE=key exchange
  • 802.1X: Supplicant (client) → Authenticator (switch/WAP) → Authentication Server (RADIUS)
  • Site-to-site VPN = router-to-router | Remote access VPN = client-to-site
  • Clientless VPN = browser/TLS portal on 443, no installed client, reaches published apps only
  • Full tunnel = all traffic via corporate (inspection, but a bottleneck) | Split tunnel = corporate traffic only (fast, but uninspected internet)
  • Jump box = bastion host; all admin access goes through it first
  • OOB = separate management path; survives production network failure
  • Console = ultimate OOB; direct serial/USB; always accessible
