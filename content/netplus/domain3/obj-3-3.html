3.3 Disaster Recovery Concepts

RPO vs RTO — Most Tested DR Terms

TermDefinitionSimple Question
RPO
(Recovery Point Objective)		 Maximum acceptable data loss, measured in time. How old can the restored data be? "How much data can we afford to lose?" → If RPO = 4 hours, backups must run every 4 hours.
RTO
(Recovery Time Objective)		 Maximum acceptable downtime. How quickly must systems be restored? "How long can we be down?" → If RTO = 1 hour, systems must be back up within 1 hour of failure.
MTTR
(Mean Time to Repair)		 Average time to restore a failed system/component. Lower MTTR = faster recovery capability.
MTBF
(Mean Time Between Failures)		 Average time between system failures. Higher MTBF = more reliable system. Used in hardware specs.

Backup Types

TypeWhat's Backed UpArchive Bit AfterRestore TimeStorage
Full All data, regardless of change Cleared Fastest (1 backup set) Most space
Incremental Only data changed since last backup (full or incremental) Cleared Slowest (need full + all incrementals) Least space
Differential All data changed since last full backup NOT cleared Medium (need full + latest differential) Grows over time until next full

Disaster Recovery Site Types

Site TypeDescriptionRTOCost
Hot Site Fully operational duplicate — live systems, real-time data replication. Just redirect traffic. Minutes to hours Very high
Warm Site Partially equipped — hardware present, data restored from backups. Some configuration needed. Hours to days Medium
Cold Site Just a space with power/connectivity — no hardware or data. Must provision everything. Days to weeks Lowest
Cloud DR Cloud-based failover — spin up cloud resources in another region on-demand. Minutes to hours (with automation) Pay-as-you-go

High Availability Concepts

  • Redundancy: Duplicate critical components — dual power supplies, redundant network links, multiple ISPs.
  • Failover: Automatic switch to a backup system when the primary fails — see the active-active vs active-passive comparison below.
  • Load Balancing: Distributes traffic across multiple servers — improves performance AND provides failover if one server dies.
  • NIC Teaming / Bonding: Multiple NICs combined for bandwidth and redundancy. If one NIC fails, traffic continues on others.
  • UPS: Uninterruptible Power Supply — provides battery backup to bridge power outages and allow graceful shutdown.
  • Generator: Long-term power backup for extended outages (hours to days).

Active-Active vs. Active-Passive

Both designs survive the loss of a node. The difference is what the second node is doing before the failure — and what you lose when the failure happens.

AspectActive-ActiveActive-Passive
Normal operation All nodes carry traffic simultaneously One node carries all traffic; the standby sits idle
Usable capacity Aggregate of all nodes — you get what you paid for Capacity of one node; the standby's capacity is bought and unused
Effect of a failure Availability is preserved but capacity drops. Size each node so the survivors can absorb the load, or a failure becomes an overload Availability is preserved and capacity is unchanged — the standby was sized to take the whole load
Failover behaviour Often seamless — traffic is already distributed, so sessions on surviving nodes are untouched Brief interruption while the standby detects the failure and assumes the role
Complexity Higher — requires load distribution and state synchronization between active nodes Lower — simpler to configure, test, and reason about
Where You Have Already Seen This — FHRP

The first hop redundancy protocols in 2.1 are these two models applied to default gateways. HSRP (Active/Standby) and VRRP (Master/Backup) are active-passive — one router owns the virtual IP and the other waits. GLBP is effectively active-active — the AVG hands out virtual MACs so multiple forwarders carry traffic at the same time. Same trade-off, different layer.

Disaster Recovery Testing

A DR plan that has never been exercised is an assumption, not a capability. The exam distinguishes two testing types, and the line between them is discussion vs. execution.

AspectTabletop ExerciseValidation Test
What happens Stakeholders talk through a scenario in a room — "the primary data centre has lost power, walk me through what you do" The failover is actually performed — services are cut over to the DR site and verified
Systems touched None. No configuration changes, no failover, no production risk Real systems. Carries genuine risk, so it is scheduled in a maintenance window
What it proves That the plan and the people hold up — roles are clear, contact lists are current, gaps in the documented procedure surface That the technology works — the backups restore, the standby hardware comes up, RTO and RPO are actually achievable
Cost and frequency Cheap and low-disruption, so it can run often Expensive and disruptive, so it runs far less frequently
⚠ Exam Traps
  • RPO = data loss tolerance. "We can't lose more than 2 hours of data" → RPO = 2 hours. Backup frequency must match.
  • RTO = downtime tolerance. "Systems must be back up within 4 hours" → RTO = 4 hours.
  • Differential grows larger each day (until next full). Incremental stays small (only daily changes).
  • Restore from incremental = full + EVERY incremental. Differential = full + LATEST differential only.
  • Hot site costs the most. Cold site costs the least. RTO inversely correlates with cost.
  • Tabletop = discussion, validation = execution. If the question says nobody touched a system and the team walked through a scenario, it is a tabletop exercise — no matter how realistic the scenario was.
  • Active-active does not mean "more available" than active-passive — both survive a node loss. Active-active loses capacity on failure; active-passive wastes capacity while idle.
  • A tabletop exercise cannot prove RTO or RPO are achievable — only a validation test does that.
Quick Recall — 3.3
  • RPO = how much data can be lost (backup frequency) | RTO = how fast to recover (downtime tolerance)
  • Full = all data | Incremental = changes since last backup (fast backup) | Differential = changes since last full
  • Hot site = live systems, minutes to recover | Warm = hours | Cold = days
  • MTBF = reliability (time between failures) | MTTR = recovery speed
  • Active-active = all nodes serve traffic, aggregate capacity, failure cuts capacity
  • Active-passive = standby idle until failover, simpler, capacity unchanged on failure
  • FHRP mapping (2.1): HSRP and VRRP = active-passive | GLBP = active-active
  • Tabletop = discussion-based walkthrough, no systems touched | Validation test = real failover executed
