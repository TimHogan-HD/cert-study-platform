PBQ Lab · Objectives 5.3, 5.5

CLI Troubleshooting Labs

Four console simulations. Investigate with the commands each device accepts, then answer the questions underneath.

How to work a console PBQ
Run every command on every device before you answer. Type help on a device to list what it accepts. Cisco devices take abbreviations (sh mac add, sh ip int br), and the up arrow recalls your last command. Nothing in the output is highlighted for you, just as in the exam.
Simulation 1 · Network discovery

Locate a device on the network

A print job keeps failing to reach a network printer at 10.10.20.57. Before you walk over to it, find out exactly where it is plugged in. You have console access to the router R1 and the two switches SW1 and SW2.

Identify the printer's MAC address, the switch and port it connects to, and its VLAN.

Console
Explanation
  1. IP to MAC: only a Layer 3 device has the ARP entry. show arp on R1 maps 10.10.20.57 to 00a0.c914.7e21. The entry for .41 is 00a0.c914.7e12: the last two hex digits are swapped, which is exactly the trap the exam sets.
  2. MAC to port on SW1: show mac address-table on SW1 lists 00a0.c914.7e21 on Gi0/2. show interfaces trunk shows Gi0/2 is a trunk, so the printer is further downstream. show cdp neighbors says Gi0/2 leads to SW2.
  3. MAC to port on SW2: SW2 learned the MAC on Fa0/14, which is not a trunk. show vlan brief puts Fa0/14 in VLAN 20 (PRINTERS), matching the router subinterface Gi0/0.20 that answered ARP.

The rule to remember: a MAC learned on a trunk port is never the final answer. Follow CDP to the next switch and repeat until the MAC appears on an access port.

Simulation 2 · No network access

One accounting PC cannot reach anything

Yesterday a technician moved workstation ACCT-07 to a different port on the access switch SW-ACC. Today the user cannot reach file shares, email, or the internet. Every other PC in Accounting works. Accounting is VLAN 30 (10.10.30.0/24), and R1 is the DHCP server for that VLAN.

Investigate from the PC, the access switch, and the router, then identify the cause and the fix.

Console
Explanation
  • 169.254.x.x with a /16 mask and no gateway is APIPA. Windows assigns it to itself when DHCP gets no answer. It is a symptom, not a cause, so the next question is why DHCP failed.
  • The pool is not the problem: show ip dhcp pool shows 23 of 254 addresses leased, and the other PCs got leases.
  • The trunk is not the problem: it carries VLAN 30, and the PCs on Fa0/5, Fa0/6, and Fa0/8 work through it.
  • The cable is not the problem: Fa0/7 is connected at 100 Mbps full duplex and the switch learned the PC's MAC on it.
  • The cause: show vlan brief and show interfaces status both put Fa0/7 in VLAN 1. Its running config has no switchport access vlan line, so it defaults to VLAN 1, where no DHCP server is listening. Compare Fa0/6.
  • The fix is interface fa0/7 then switchport access vlan 30. Then run ipconfig /renew on the PC to verify, which is step 6 of the methodology. Renewing before the fix only repeats the failure.
Simulation 3 · Name resolution

Websites will not load on one PC

A user on HR-02 says no websites load, internal or external, and the intranet at intranet.acme.internal times out. The user at HR-03 on the next desk has no problems. Last month the old DNS server 10.20.9.53 was retired and replaced by 10.20.0.53.

Use both PCs to find out what is different about HR-02.

Console
Explanation
  • Layer 3 works: ping 8.8.8.8 and tracert 8.8.8.8 succeed from HR-02, so the address, mask, gateway, and routing are fine. When an IP address works but a name does not, the problem is name resolution.
  • The difference: ipconfig /all shows HR-02 has DHCP Enabled: No and a DNS server of 10.20.9.53, the retired server. nslookup times out against it and it does not answer ping. HR-03 gets its settings from DHCP and uses 10.20.0.53, which resolves the intranet name.
  • Why not flush the cache: flushing only empties cached answers. HR-02 still asks a server that no longer exists.
  • The fix is to switch HR-02 back to DHCP, which is how the rest of the floor is configured. Typing 10.20.0.53 in by hand also works, but it leaves a static setting that the next server change will break again.
Simulation 4 · Performance

Slow transfers from the third floor

Since a core switch was swapped over the weekend, every user on the third floor reports that file copies to the data center crawl and video calls stutter. The floor switch SW-FLOOR3 uplinks to SW-CORE. Nobody has touched SW-FLOOR3.

Compare the two ends of the uplink and decide what to change.

Console
Explanation
  • The weekend change: the new core port was configured with speed 100 and duplex full. A port with hard-set speed and duplex stops auto-negotiating. SW-FLOOR3 still auto-negotiates, so it detects the speed from the signal (100 Mbps) but cannot learn the duplex, and the standard fallback is half duplex. show interfaces status shows the result: a-half on the floor switch and a hard-set full on the core.
  • The counters agree: the half-duplex side records late collisions, because it is still listening for collisions while the full-duplex side transmits whenever it likes. The full-duplex side records CRC errors and runts, which are the frames the half-duplex side cut off part-way through. The syslog %CDP-4-DUPLEX_MISMATCH message says it outright.
  • Why not the cable: CRC errors alone could mean a bad cable, but a cable fault does not produce late collisions on the other end, and it does not appear on the same night as a configuration change.
  • The fix: make both ends negotiate (speed auto, duplex auto on SW-CORE Gi1/0/2), or hard-set both ends to the same values. Setting the floor side to half only makes the mismatch official, and bouncing the port renegotiates into the same mismatch.
