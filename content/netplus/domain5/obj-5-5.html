Protocol Analyzer

A protocol analyzer captures frames off the wire and decodes them layer by layer. Wireshark is the reference implementation; tcpdump is the command-line equivalent that writes the same .pcap format. The analyzer is the tool of last resort in a troubleshooting flow — you reach for it when the symptom and the configuration disagree and you need to see what is actually being transmitted.

Capture Filter vs. Display Filter — The Exam Distinction

Capture filter is applied before packets are written. It uses BPF syntax (host 10.1.1.5, tcp port 443) and is the same syntax tcpdump takes. Anything it excludes is gone permanently — it was never recorded.

Display filter is applied after capture, to what is already saved. It uses Wireshark's own syntax (ip.addr == 10.1.1.5, tcp.port == 443, http.response.code == 404) and is non-destructive — clear the filter and the full capture is still there.

Practical rule: capture filter on a busy link to keep the file manageable; display filter for everything else. If you are not sure what you are looking for yet, capture wide and filter on display.

Following a stream reassembles one conversation out of the capture. In Wireshark, right-click a packet → Follow → TCP Stream shows the entire session's payload in order, with each side colour-coded, and automatically sets a display filter for that stream. This is how you read a plaintext protocol exchange — an HTTP request and response, an FTP login, an SMTP conversation — without reading packet-by-packet.

Speed Tester

A speed tester measures achieved throughput over a path. Browser-based testers (the ones an ISP or a user will run) open several parallel connections to a nearby internet server and report download, upload, and latency. CLI equivalents exist for headless hosts and for scripted/scheduled measurement.

Speed Tester vs. iperf3 — What Each One Actually Measures

Speed test to an internet server measures the whole path: the client NIC, the LAN, the firewall, the WAN link, the ISP's network, and the peering to the test server. A poor result proves something on that path is slow — it does not tell you which hop.

iperf3 measures point-to-point between two endpoints you control: you run iperf3 -s on one and iperf3 -c on the other. Because you choose both ends, you can bisect the path — test across the LAN first, then across the WAN, and the segment where the number drops is the bottleneck.

Exam framing: "verify the circuit delivers the contracted bandwidth" → speed tester against the provider. "Isolate which segment is slow" → iperf3 between controlled endpoints. See 5.3 for iperf3 syntax.

show route — the routing table

Answers "does this device know a path to the destination, and which one will it use?" Read it when traffic to one network fails while everything else works. The first letter on each line is the source of the route — C connected, S static, O OSPF, D EIGRP, B BGP — and S* marks the candidate default route.

Cisco IOS — show ip route
Router1# show ip route
Codes: C - connected, S - static, O - OSPF, D - EIGRP, B - BGP
       * - candidate default

S*   0.0.0.0/0 [1/0] via 203.0.113.1           ← default route present ✓
C    10.1.1.0/24 is directly connected, GigabitEthernet0/0
O    10.1.20.0/24 [110/2] via 10.1.1.2, GigabitEthernet0/0
S    192.168.50.0/24 [1/0] via 10.1.1.9
# [110/2] = [administrative distance / metric]
# No entry for a destination + no default route = packet is dropped

show interface — port state and counters

Answers "is this port working, and working correctly?" Two lines carry most of the diagnostic value: the up/down line and the error counters. Note the two halves of the status line mean different things — interface is up is Layer 1 (a signal is present) and line protocol is up is Layer 2 (keepalives are being exchanged). Layer 1 up with Layer 2 down points at an encapsulation or keepalive mismatch, not a cable fault.

Cisco IOS — show interfaces
Switch1# show interfaces GigabitEthernet0/3
GigabitEthernet0/3 is up, line protocol is up   ← L1 up, L2 up = healthy
  Hardware is Gigabit Ethernet, address is 0050.7966.6800
  MTU 1500 bytes, BW 1000000 Kbit/sec
  Full-duplex, 1000Mb/s, media type is 10/100/1000BaseTX
  5 minute input rate 4210000 bits/sec, 620 packets/sec
     0 runts, 0 giants, 0 throttles
     0 CRC, 0 frame, 0 overrun, 0 ignored
     0 output errors, 0 collisions, 0 late collision
# Counters at zero and full-duplex = no physical or duplex problem here
# Incrementing CRC + runts + late collisions = duplex mismatch — see 5.2
# "up / line protocol down" = L1 fine, L2 broken (encapsulation, keepalives)

show config — running vs. startup

Answers "what is this device configured to do?" — and, critically, whether that configuration will survive a reboot. IOS keeps two copies: the running configuration in RAM, which is live and lost on power cycle, and the startup configuration in NVRAM, which is what loads at boot. An unsaved change works perfectly until the device restarts, at which point the fault reappears with no apparent cause.

Cisco IOS — running vs startup config
Switch1# show running-config          ← live config in RAM
Switch1# show startup-config          ← config in NVRAM, loads at boot

Switch1# show running-config interface GigabitEthernet0/3
interface GigabitEthernet0/3
 switchport access vlan 10
 switchport mode access
 spanning-tree portfast

Switch1# copy running-config startup-config   ← save, or the change dies at reboot
[OK]
# "The fix worked, then the problem came back after a reboot" = never saved

show power — PoE allocation and budget

Answers "why will this powered device not come up?" The switch has a fixed PSE budget shared across all ports; once it is consumed, further devices simply do not power on even though the ports are physically fine. Compare Available against Used first, then check the per-port class. The budget mechanics and the 802.3af/at/bt power levels are covered in 2.4 — here the use is purely diagnostic.

Discovery Protocols

Discovery protocols let a device tell you what is plugged into it. They are the fastest way to map an undocumented network and to answer "what is on the other end of this cable?" without walking the cable — which makes them a natural fit for the network-discovery workflow in 5.3.

The Operational Point That Gets Missed

Discovery protocols show only directly connected devices. CDP and LLDP frames are consumed by the first device that receives them — a switch does not forward them onward. A router connected to a switch will therefore list that switch and nothing beyond it, no matter how many devices hang off it.

This is the most common real-world misunderstanding of these protocols and a likely exam item. To map a multi-switch topology you walk it hop by hop: run show cdp neighbors, connect to a neighbour it reports, run it again there, and repeat. Each run adds one tier.

Cisco IOS — show cdp neighbors
Switch1# show cdp neighbors
Capability Codes: R - Router, T - Trans Bridge, B - Source Route Bridge
                  S - Switch, H - Host, I - IGMP, r - Repeater, P - Phone

Device ID    Local Intrfce   Holdtme  Capability  Platform    Port ID
Switch2      Gig 0/1          142         S I     WS-C2960    Gig 0/24
Router1      Gig 0/2          173        R S I    ISR4331     Gig 0/0/0
AP-Floor2    Gig 0/5          165         H       AIR-AP2802  Gig 0
# Device ID    = neighbour's hostname
# Local Intrfce = MY port it is plugged into
# Port ID      = THEIR port at the far end — the two are easy to transpose
# Holdtme      = seconds left before the entry ages out (CDP default 180)
# Only these three appear — anything behind Switch2 is invisible from here

show cdp neighbors detail adds the two fields the summary omits and that you usually actually want — the neighbour's IP address and its IOS version. The IP address is what makes this a discovery tool rather than a cabling report: it gives you the address to connect to for the next hop of the walk.

LLDP-MED Is Not LLDP

LLDP-MED (MED — Media Endpoint Discovery) is an extension to LLDP for voice and media endpoints, not a synonym for it. It adds what an IP phone specifically needs: automatic voice VLAN assignment, fine-grained PoE power negotiation beyond the basic classes, and location information for E911 emergency calling.

A switch can run plain LLDP and still not hand a phone its voice VLAN — that requires LLDP-MED. Treat "LLDP is enabled, so the phone will configure itself" as a false statement.

Security Trade-off

Discovery protocols advertise hostname, platform model, IOS version, and port — useful to you, and equally useful to an attacker with access to a port. Common hardening practice is to disable them on untrusted or edge-facing interfaces (no cdp enable per interface, no cdp run globally) while leaving them on between infrastructure devices.

Taps

A network tap (Test Access Point) is a physical device inserted inline on a cable. It passes traffic through unchanged and copies every frame out a monitor port. Because the copying is done in hardware on the cable itself, the tap sees everything on that link and cannot be turned off, reconfigured, or overloaded by the switch.

Tap vs. SPAN — Hardware vs. Software

Tap — passive hardware. Inline on the physical cable. Copies at line rate including errored frames and Layer 1 problems. No switch CPU or backplane involvement. Requires physically breaking the link to install, so it means downtime to deploy and it monitors exactly one link.

SPAN / port mirroring — switch software. Configured on the switch to copy traffic from chosen ports or VLANs to a monitor port. Deployed instantly with no cabling change and can mirror many sources. But it is a software function competing for switch resources: under heavy load the switch will drop mirrored frames first, it normally discards errored frames and other Layer 1 artefacts, and an attacker with switch access can disable it.

Exam framing: "must not miss a single frame", "evidence-grade capture", or "cannot be disabled by an attacker" → tap. "Add monitoring without downtime" or "mirror several VLANs" → SPAN. Traffic mirroring configuration is covered in 3.2.

⚠ Exam Traps
  • CDP and LLDP show directly connected devices only — a neighbour's neighbours are never listed. Walk the topology hop by hop.
  • LLDP-MED ≠ LLDP. Plain LLDP does not assign a voice VLAN; LLDP-MED does.
  • CDP is Cisco-proprietary; LLDP is IEEE 802.1AB. In a mixed-vendor scenario the answer is LLDP.
  • In show cdp neighbors, Local Intrfce is your port and Port ID is theirs — reading them backwards inverts the topology you draw.
  • show cdp neighbors alone does not give you the neighbour's IP address — you need detail.
  • Capture filter discards permanently before writing; display filter only hides what is already saved.
  • Speed tester measures the whole path to the internet; iperf3 measures between two endpoints you control. Only iperf3 can bisect a path.
  • A tap is passive hardware and cannot drop frames under load; SPAN is a switch software feature and drops mirrored traffic first when the switch is busy.
  • "Interface is up, line protocol is down" is a Layer 2 problem — not a cable fault.
  • A fix that survives testing but disappears after a reboot was never written to the startup configuration.
  • A PoE port showing off with no fault may simply mean the switch budget is exhausted — check show power inline before replacing the port or the device.
  • CompTIA writes show route and show power; Cisco devices take show ip route and show power inline. Expect CompTIA's spelling in the question.
