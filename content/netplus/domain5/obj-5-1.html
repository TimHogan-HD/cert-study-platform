Objective 5.1

Troubleshooting Methodology

CompTIA defines a specific 7-step troubleshooting methodology. Memorize the exact wording — the exam tests the correct order and exact step names, not just the concept.

The 7-Step Methodology (exact CompTIA wording)

1
Identify the problem
Gather information, question users, identify symptoms, determine if anything has changed, duplicate the problem if possible, approach multiple problems individually
2
Establish a theory of probable cause
Question the obvious; consider multiple approaches — top-to-bottom/bottom-to-top OSI model, divide and conquer. Start with the simplest explanation (Occam's razor)
3
Test the theory to determine the cause
If confirmed → move to step 4. If not confirmed → establish new theory or escalate
4
Establish a plan of action to resolve the problem and identify potential effects
Before touching anything, plan the fix and consider side effects
5
Implement the solution or escalate as necessary
Apply fix. If outside your scope, escalate to appropriate tier
6
Verify full system functionality and, if applicable, implement preventive measures
Confirm fix works end-to-end. Consider what prevents recurrence
7
Document findings, actions, outcomes, and lessons learned throughout the process
Update tickets, knowledge base, runbooks. Documentation is always the last step
Step 1 — The Three Sub-Steps Candidates Skip

Determine if anything has changed. This is an enumerated part of step 1, not a later step. Most faults follow a change — a patch, a config push, a new device, a cable moved. Asking "what changed?" early is what makes step 2 quick.

Duplicate the problem, if possible. "If possible" is part of the official wording. An intermittent fault you cannot reproduce is not a dead end — you proceed with the evidence you have rather than stalling here.

Approach multiple problems individually. If a user reports three symptoms, they may be three separate faults or one root cause. Treat each as its own thread until proven related — bundling them is how a single root cause gets missed.

Checking event logs is part of gathering information in practice, but CompTIA does not enumerate it as a sub-step. Do it — just do not expect it as an answer option.

Scenario Walkthrough 1: User Can't Access Shared Drive

7-Step Applied
  1. Identify: User reports "can't access \\server01\data". Error: "Network path not found." Only this user affected.
  2. Theory: DNS resolution failure, VLAN misconfiguration, or incorrect credentials.
  3. Test theory: ping server01 fails. ping 10.1.1.50 (IP) succeeds. Conclusion: DNS issue, not routing.
  4. Plan: Flush DNS cache, check DHCP option 6 assignment. No impact to other users.
  5. Implement: ipconfig /flushdns. Assign correct DNS via DHCP. Test.
  6. Verify: User can reach share by name. Ping server01 resolves correctly. Check two other machines — confirm no broader issue.
  7. Document: Ticket updated: "DHCP option 6 was pointing to decommissioned DNS server 10.1.1.5. Corrected to 10.1.1.10."
PowerShell — Scenario 1: DNS vs routing
PS C:\> ping server01
Ping request could not find host server01.    ← DNS resolution failed
Please check the name and try again.

C:\> ping 10.1.1.50
Pinging 10.1.1.50 with 32 bytes of data:
Reply from 10.1.1.50: bytes=32 time=2ms TTL=128   ← IP works! Layer 3 is fine
Reply from 10.1.1.50: bytes=32 time=1ms TTL=128
# Name fails + IP works = DNS problem, not a routing or connectivity issue

C:\> ipconfig /flushdns
Windows IP Configuration
Successfully flushed the DNS Resolver Cache.

# After DHCP option 6 corrected to 10.1.1.10:
C:\> ping server01
Reply from 10.1.1.50: bytes=32 time=2ms TTL=128   ← name resolves now ✓

Scenario Walkthrough 2: Intermittent Connectivity

7-Step Applied
  1. Identify: Multiple users on same floor report random drops, 2-5 seconds, several times/hour. Started after weekend maintenance.
  2. Theory: STP topology change, duplex mismatch on uplink, or failing switch port. Maintenance correlates strongly.
  3. Test: Check show interface on uplink — CRC errors, runts detected. Check duplex settings: access switch = half-duplex, core switch = full-duplex.
  4. Plan: Configure both ends to full-duplex / 1G. Brief outage expected during port reset.
  5. Implement: Set duplex full on both interface sides. Port bounces.
  6. Verify: CRC errors stop incrementing. Users report stable connectivity for 30 minutes. Monitor interface counters.
  7. Document: Root cause: duplex mismatch introduced when access switch was replaced during weekend maintenance. New switch defaulted to auto-negotiate; core switch was hardcoded to half-duplex.
Cisco IOS — Scenario 2: duplex mismatch
Switch# show interface GigabitEthernet0/1
GigabitEthernet0/1 is up, line protocol is up
  Hardware is Gigabit Ethernet
  MTU 1500 bytes, BW 100000 Kbit/sec
  Half-duplex, 100Mb/s   ← mismatch: core switch is full-duplex

  5 minute input rate 1200000 bits/sec, 890 packets/sec
  127 CRC, 45 runts, 0 giants   ← CRC + runts together = duplex mismatch signature
  0 input errors, 0 output errors
# CRC errors = frame corruption from collisions caused by half/full mismatch
# Runts = frames <64 bytes, caused by collisions truncating packets
# Fix: set both ends to "duplex full" or both to "duplex auto"

Scenario Walkthrough 3: No Internet Access

7-Step Applied
  1. Identify: All users in building B can't reach internet. Internal resources work fine. Started ~1 hour ago.
  2. Theory: WAN link down, default route missing, firewall policy change, or NAT misconfiguration.
  3. Test: ping 8.8.8.8 from router fails. show ip route — no default route (0.0.0.0/0) present.
  4. Plan: Re-add static default route or restore BGP session. Check for change log entry.
  5. Implement: Restore static route ip route 0.0.0.0 0.0.0.0 [ISP-GW]. Verify BGP neighbor if applicable.
  6. Verify: ping 8.8.8.8 succeeds. HTTP/HTTPS confirmed working from end stations.
  7. Document: Default route was removed during an ACL cleanup script that ran automatically. Added exception and updated automation script.
Cisco IOS — Scenario 3: missing default route
Router# ping 8.8.8.8
Sending 5, 100-byte ICMP Echos to 8.8.8.8, timeout is 2 seconds:
.....                    ← 5 dots = 100% packet loss (. = timeout, ! = success)
Success rate is 0 percent (0/5)

Router# show ip route
C    10.0.0.0/30    is directly connected, GigabitEthernet0/0
C    192.168.1.0/24 is directly connected, GigabitEthernet0/1

🎯 PBQ Prep — Troubleshooting Simulation

What it looks like: Given a network diagram with a reported outage, you click devices to view their output and identify the fault.

Strategy: Always start by pinging — does Layer 3 work? If yes, problem is above Layer 3. If no, check routing table then physical. Check interface errors for duplex/speed mismatches.

Common traps: Don't fix the symptom — fix the root cause. Step 3 says "test the theory" before implementing. On the exam, selecting "implement fix" before "test theory" is wrong.

⚠ Exam Traps
  • "Implement the solution" is step 5, not step 4 — step 4 is planning the fix
  • "Document" is always the last step (step 7), even if you think you should document earlier
  • If theory doesn't confirm in step 3, you go back to step 2 — not skip to step 5
  • Escalation happens in step 5, not before establishing a theory
  • "Determine if anything has changed" belongs to step 1 — it is part of identifying the problem, not a separate later step
  • "Approach multiple problems individually" is also step 1. Several simultaneous symptoms are treated as separate problems until proven otherwise — do not assume one root cause.
  • Step 1 says "duplicate the problem, if possible" — being unable to reproduce an intermittent fault does not stop you progressing to step 2
  • Step 7 includes lessons learned throughout the process — an answer that stops at "findings, actions, and outcomes" is the incomplete one
✓ Quick Recall
  • Step 1: Identify the problem
  • Step 2: Theory of probable cause
  • Step 3: Test the theory
  • Step 4: Plan of action (with potential effects)
  • Step 5: Implement or escalate
  • Step 6: Verify + preventive measures
  • Step 7: Document findings, actions, outcomes, and lessons learned throughout the process
  • Documentation = always last
  • Step 1 in full: gather information · question users · identify symptoms · determine if anything has changed · duplicate the problem if possible · approach multiple problems individually
  • Three approaches: top-down (L7→L1), bottom-up (L1→L7), divide and conquer (start middle)
