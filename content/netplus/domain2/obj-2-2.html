Objective 2.2

Switching & VLANs

VLANs and STP are among the most-tested topics in Domain 2. Expect both MCQ and PBQ coverage.

VLAN Segmentation — Separate Broadcast Domains

Switch MAC Address Table Operation

  1. Switch receives a frame — records source MAC + incoming port in the MAC address table.
  2. Looks up destination MAC in the table.
  3. If found: forwards frame out only that port (unicast).
  4. If not found: floods frame out all ports except incoming (unknown unicast flood).
  5. MAC entries age out after 300 seconds (default) if not refreshed.

VLAN Concepts

VLANs create separate broadcast domains on a single physical switch. Benefits: security isolation, traffic management, reduced broadcast domains.

Port TypeDescriptionConfiguration
Access Port Belongs to one VLAN; carries untagged traffic. Connects to end devices. switchport mode access
switchport access vlan 10
Trunk Port Carries traffic for multiple VLANs; uses 802.1Q tags. Connects switches or routers. switchport mode trunk
switchport trunk allowed vlan 10,20,30
Native VLAN Traffic sent untagged on a trunk port. Default VLAN 1 on Cisco. Must match on both ends! switchport trunk native vlan 99
Voice VLAN Dedicated VLAN for VoIP traffic. QoS and segmentation for phones. switchport voice vlan 100
REMEMBER THIS
Default VLAN = VLAN 1 (cannot be deleted on Cisco IOS). Native VLAN on a trunk carries untagged frames — must match on both ends or you get VLAN hopping risk. Voice VLAN rides alongside data on access ports for IP phones (typically tagged with 802.1p priority).

The VLAN Database

VLAN definitions do not live in the running configuration. A switch keeps them in a separate VLAN database — on Cisco IOS this is a file called vlan.dat stored in flash memory. The running-config records only which VLAN a port belongs to; the VLAN itself is defined elsewhere.

Why this matters — the config-restore trap

Because vlan.dat is separate from the running-config, restoring a configuration backup does not restore your VLANs. A switch rebuilt from a saved config comes up with access ports assigned to VLANs that no longer exist — the ports go inactive and the attached hosts lose connectivity, even though the config file looks completely correct. Erasing the startup-config with erase startup-config also leaves vlan.dat untouched; a genuine reset to factory defaults requires delete flash:vlan.dat as a separate step.

Cisco IOS — the VLAN database is a separate file
Switch1# show flash:

Switch1# show running-config | include vlan

# ...but the definition of VLAN 10 itself is not here — it lives in vlan.dat

Switch1# erase startup-config
Erasing the nvram filesystem... [OK]
! vlan.dat still present — VLANs survive this

Switch1# delete flash:vlan.dat     ← required for a true factory reset

VTP — Propagating the Database

VTP is a Cisco protocol that synchronises the VLAN database across all switches in a shared VTP domain, so a VLAN created once on a server-mode switch appears everywhere. Every database change increments a configuration revision number, and switches accept any update carrying a higher revision number than their own.

VTP ModeCan create/delete VLANs?Behaviour
ServerYesDefault mode. Creates, modifies, and deletes VLANs; advertises the database to the domain.
ClientNoReceives and applies the database from servers; forwards advertisements but cannot make local changes.
TransparentYes — locally onlyKeeps its own independent database, forwards advertisements without applying them. Revision number stays 0.
REMEMBER THIS
The classic VTP disaster: a switch removed from the network, used in a lab, then plugged back in arrives with a higher revision number than the production domain. Its stale database propagates and overwrites every switch in the domain — deleting production VLANs network-wide. This is why a switch should always be set to transparent mode (or have its revision reset) before being reintroduced. Note that revision number, not VTP mode, decides the winner: a client with a higher revision number will still overwrite a server.

802.1Q Trunk Tagging

802.1Q adds a 4-byte tag inside the Ethernet frame after the source MAC address:

  • TPID: 0x8100 — identifies this as an 802.1Q frame
  • Priority (PCP): 3-bit QoS markings (0–7)
  • VLAN ID (VID): 12-bit VLAN identifier (1–4094)

EtherChannel / LACP

EtherChannel bundles multiple physical links into one logical link — more bandwidth and redundancy without STP blocking the redundant links (STP treats the bundle as one link).

  • LACP (802.3ad) — Open standard; preferred. Dynamically negotiates EtherChannel.
  • PAgP — Cisco proprietary EtherChannel negotiation.
  • Static (mode on) — Forces EtherChannel without negotiation.

Interface Configuration — Speed and Duplex

Every switch port has a speed and a duplex setting. Both default to auto-negotiation, where the two ends exchange capabilities and agree on the highest common denominator.

The Auto/Hardcode Mismatch

Auto-negotiation only works when both ends are set to auto. If one end is hardcoded and the other is left on auto, the auto side can still detect the correct speed by sensing the signal — but it has no way to detect duplex, so it falls back to half duplex. The result is a link that comes up successfully at the right speed with one end full and the other half: a duplex mismatch that degrades badly under load while looking healthy in show interface status.

The fix is to be consistent: set both ends to auto, or hardcode both ends to the same values. Never mix the two.

MTU and Jumbo Frames

MTU (Maximum Transmission Unit) is the largest payload a single frame can carry. The Ethernet default is 1500 bytes — that is the IP packet size, not counting the 18-byte Ethernet header and trailer, which is why a standard full-size Ethernet frame is 1518 bytes on the wire.

When a packet exceeds the MTU of the next link, one of two things happens: it is fragmented into smaller pieces, or — if the Don't Fragment bit is set, and always in IPv6 — it is dropped and an ICMP "fragmentation needed" message is returned to the sender. Path MTU Discovery relies on exactly those ICMP messages to find the smallest MTU along a path. If a firewall blocks ICMP, PMTUD silently fails and large packets vanish while small ones (like pings) succeed — the classic "web pages hang but the server responds to ping" symptom.

Standard FrameJumbo Frame
MTU (payload)1500 bytesTypically 9000 bytes
Frame size on wire1518 bytes~9018 bytes
Overhead per byte movedHigher — more frames, more headers, more CPU interruptsLower — one header serves six times the data
Where usedEverywhere by default; required across the internetStorage networks (iSCSI, NFS, FCoE), data centre east-west traffic, backup and replication networks
Jumbo Frames Require End-to-End Support

Every device in the path must support and be configured for jumbo frames — both hosts, every switch, and every router in between. There is no negotiation. A single device left at the 1500-byte default will drop the oversized frames it receives, counting them as giants, or force fragmentation that erases the entire performance benefit. This is why jumbo frames are confined to controlled environments like a storage VLAN or a data centre fabric, and never enabled on paths that traverse the internet.

⚠ Exam Traps
  • STP states ≠ STP roles. States = what the port is doing (Forwarding/Blocking). Roles = why it was chosen (Root/Designated).
  • Native VLAN must match on both ends of a trunk link. Mismatch = frames go to wrong VLAN (and this is a VLAN hopping attack vector).
  • PortFast should ONLY be on access ports. Enabling on a trunk port = potential STP loop.
  • RSTP replaces Blocking + Listening + Disabled with a single "Discarding" state — question might test which RSTP states exist.
  • Root bridge = switch with lowest Bridge ID (bridge priority + MAC). Default priority = 32768; lower wins.
  • Jumbo frames must be supported by every device in the path. One switch left at 1500 bytes drops them as giants. There is no negotiation and no partial deployment.
  • The VLAN database is separate from the running-config. Restoring a config backup does not restore VLANs — vlan.dat must be handled separately. erase startup-config does not remove it.
  • A VTP switch with a higher revision number overwrites the domain — including a client overwriting a server. Reset the revision (or use transparent mode) before reintroducing an old switch.
  • Hardcoding one end of a link and leaving the other on auto gives you the correct speed but half duplex on the auto side. The link comes up; the mismatch is silent until load exposes it.
Quick Recall — 2.2
  • Access port = one VLAN, untagged | Trunk port = multiple VLANs, 802.1Q tagged
  • Native VLAN = untagged traffic on trunk; must match both ends
  • STP: Blocking → Listening → Learning → Forwarding (30–50s total)
  • RSTP: Discarding → Learning → Forwarding (<1s)
  • Root bridge = lowest Bridge ID | Root port = lowest cost path to root
  • PortFast + BPDU Guard = safe access port config; BPDU Guard shuts port if switch connects
  • VLAN database = vlan.dat in flash, separate from running-config; survives erase startup-config
  • VTP modes: Server (create/advertise) | Client (receive only) | Transparent (local only, revision stays 0)
  • VTP: highest configuration revision number wins — even a client can overwrite a server
  • MTU default = 1500 bytes payload (1518-byte frame) | Jumbo = 9000 bytes
  • Jumbo frames need path-wide support — one non-jumbo device drops them as giants
  • Auto on one end + hardcoded on the other = right speed, half duplex, silent mismatch
