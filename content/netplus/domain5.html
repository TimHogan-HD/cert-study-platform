Objective 5.1

Troubleshooting Methodology

CompTIA defines a specific 7-step troubleshooting methodology. Memorize the exact wording — the exam tests the correct order and exact step names, not just the concept.

The 7-Step Methodology (exact CompTIA wording)

1
Identify the problem
Gather information, question users, identify symptoms, duplicate the issue, check event logs
2
Establish a theory of probable cause
Question the obvious, consider multiple approaches, start with simplest explanation (Occam's razor)
3
Test the theory to determine the cause
If confirmed → move to step 4. If not confirmed → establish new theory or escalate
4
Establish a plan of action to resolve the problem and identify potential effects
Before touching anything, plan the fix and consider side effects
5
Implement the solution or escalate as necessary
Apply fix. If outside your scope, escalate to appropriate tier
6
Verify full system functionality and, if applicable, implement preventive measures
Confirm fix works end-to-end. Consider what prevents recurrence
7
Document findings, actions, and outcomes
Update tickets, knowledge base, runbooks. Documentation is always the last step

Scenario Walkthrough 1: User Can't Access Shared Drive

7-Step Applied
  1. Identify: User reports "can't access \\server01\data". Error: "Network path not found." Only this user affected.
  2. Theory: DNS resolution failure, VLAN misconfiguration, or incorrect credentials.
  3. Test theory: ping server01 fails. ping 10.1.1.50 (IP) succeeds. Conclusion: DNS issue, not routing.
  4. Plan: Flush DNS cache, check DHCP option 6 assignment. No impact to other users.
  5. Implement: ipconfig /flushdns. Assign correct DNS via DHCP. Test.
  6. Verify: User can reach share by name. Ping server01 resolves correctly. Check two other machines — confirm no broader issue.
  7. Document: Ticket updated: "DHCP option 6 was pointing to decommissioned DNS server 10.1.1.5. Corrected to 10.1.1.10."

Scenario Walkthrough 2: Intermittent Connectivity

7-Step Applied
  1. Identify: Multiple users on same floor report random drops, 2-5 seconds, several times/hour. Started after weekend maintenance.
  2. Theory: STP topology change, duplex mismatch on uplink, or failing switch port. Maintenance correlates strongly.
  3. Test: Check show interface on uplink — CRC errors, runts detected. Check duplex settings: access switch = half-duplex, core switch = full-duplex.
  4. Plan: Configure both ends to full-duplex / 1G. Brief outage expected during port reset.
  5. Implement: Set duplex full on both interface sides. Port bounces.
  6. Verify: CRC errors stop incrementing. Users report stable connectivity for 30 minutes. Monitor interface counters.
  7. Document: Root cause: duplex mismatch introduced when access switch was replaced during weekend maintenance. New switch defaulted to auto-negotiate; core switch was hardcoded to half-duplex.

Scenario Walkthrough 3: No Internet Access

7-Step Applied
  1. Identify: All users in building B can't reach internet. Internal resources work fine. Started ~1 hour ago.
  2. Theory: WAN link down, default route missing, firewall policy change, or NAT misconfiguration.
  3. Test: ping 8.8.8.8 from router fails. show ip route — no default route (0.0.0.0/0) present.
  4. Plan: Re-add static default route or restore BGP session. Check for change log entry.
  5. Implement: Restore static route ip route 0.0.0.0 0.0.0.0 [ISP-GW]. Verify BGP neighbor if applicable.
  6. Verify: ping 8.8.8.8 succeeds. HTTP/HTTPS confirmed working from end stations.
  7. Document: Default route was removed during an ACL cleanup script that ran automatically. Added exception and updated automation script.
🎯 PBQ Prep — Troubleshooting Simulation

What it looks like: Given a network diagram with a reported outage, you click devices to view their output and identify the fault.

Strategy: Always start by pinging — does Layer 3 work? If yes, problem is above Layer 3. If no, check routing table then physical. Check interface errors for duplex/speed mismatches.

Common traps: Don't fix the symptom — fix the root cause. Step 3 says "test the theory" before implementing. On the exam, selecting "implement fix" before "test theory" is wrong.

⚠ Exam Traps
  • "Implement the solution" is step 5, not step 4 — step 4 is planning the fix
  • "Document" is always the last step (step 7), even if you think you should document earlier
  • If theory doesn't confirm in step 3, you go back to step 2 — not skip to step 5
  • Escalation happens in step 5, not before establishing a theory
✓ Quick Recall
  • Step 1: Identify the problem
  • Step 2: Theory of probable cause
  • Step 3: Test the theory
  • Step 4: Plan of action (with potential effects)
  • Step 5: Implement or escalate
  • Step 6: Verify + preventive measures
  • Step 7: Document
  • Documentation = always last
  • Three approaches: top-down (L7→L1), bottom-up (L1→L7), divide and conquer (start middle)

Duplex Mismatch — The Exam Favorite

Duplex Mismatch Pattern

Situation: One side of link is full-duplex, other side is half-duplex (or auto-negotiate mismatch).

Symptoms: Late collisions, runts, CRC errors on the half-duplex side; intermittent slowness; performance degrades under load.

Fix: Hard-code both ends to matching duplex and speed, or let both auto-negotiate (both sides must be set to auto).

Key rule: If one side is hardcoded and the other is auto, the auto side will negotiate speed correctly but default to half-duplex — causing a mismatch even though the link is up.

🎯 PBQ Prep — Cable Identification

What it looks like: Given a scenario description (e.g., "connecting two switches 80m apart requiring 10 Gbps") select the correct cable type and connector.

Key mappings to know cold:

  • 10G at 100m → Cat6A or fiber (Cat6 only supports 10G to 55m)
  • Long distance (>100m) → fiber (SMF for km-scale, MMF up to 550m)
  • Air-handling space → plenum-rated cable
  • Outdoor buried → direct-burial rated cable
  • Between buildings (electrical isolation) → fiber (no ground loop risk)
⚠ Exam Traps
  • OTDR is for fiber only — use TDR for copper
  • Late collisions are not the same as normal collisions — late = duplex mismatch
  • Toner probe finds a cable; loopback plug tests a port — different tools, different purposes
  • Light meter measures power (dBm); OTDR measures loss profile along the length — both are fiber tools
✓ Quick Recall
  • Late collisions + runts + CRC = duplex mismatch
  • TDR = copper, OTDR = fiber, spectrum analyzer = wireless RF
  • Loopback plug tests a port (NIC/switch); toner probe traces/identifies a cable
  • Plenum cable required in air-handling spaces (FEP/Teflon jacket)
  • Cat6 = 10G at 55m; Cat6A = 10G at 100m
  • Fiber between buildings = electrical isolation (no ground loop)

APIPA — Diagnostic Indicator

169.254.x.x — What It Means

If a Windows device self-assigns an address in 169.254.0.0/16 (APIPA — Automatic Private IP Addressing), it means DHCP failed. The device sent DHCP Discover broadcasts but received no Offer within timeout.

Diagnose: Is the DHCP server down? Is there a DHCP relay (ip helper-address) misconfigured? Is the client on the wrong VLAN where no DHCP server exists?

APIPA devices can communicate only with other APIPA devices on the same link — no internet, no cross-subnet access.

Network Discovery PBQ — Full Walkthrough

🎯 PBQ Prep — Network Discovery Simulation (Most Time-Consuming PBQ)

What it looks like: You are given a terminal connected to a switch. You have 4 available commands. You must find: the MAC address of a target device, its IP address, which VLAN it's on, and which port it connects to — possibly across multiple switches.

The 4 commands you get:

show mac address-table
show arp
show vlan
show ip interface brief

Step-by-step process:

  1. Run show ip interface brief — confirms which interfaces are up/down and which IPs belong to this switch (SVIs)
  2. Run show vlan — shows which ports are in which VLANs (access ports only; trunk ports are not listed here)
  3. Run show mac address-table — maps MAC addresses to ports. If target MAC appears on a trunk port, the device is on a downstream switch
  4. Run show arp — maps IP addresses to MAC addresses (only populated if this is a Layer 3 switch or router)

Sample output cross-reference scenario:

Switch1# show mac address-table
Vlan  Mac Address        Type    Ports
----  -----------------  ------  -----
10    0050.7966.6800     DYNAMIC Gi0/1    ← target device MAC on port Gi0/1
10    0050.7966.6801     DYNAMIC Gi0/2
20    0050.7966.6802     DYNAMIC Gi0/3

Switch1# show vlan
VLAN  Name      Status    Ports
----  --------  --------  ------
10    CORP      active    Gi0/1, Gi0/2
20    GUEST     active    Gi0/3

Switch1# show arp
Protocol  Address      Age  Hardware Addr    Interface
Internet  10.10.10.50  12   0050.7966.6800   Vlan10   ← MAC maps to IP 10.10.10.50

Conclusion: Target device MAC 0050.7966.6800 is on port Gi0/1, VLAN 10, IP address 10.10.10.50.

Multi-switch: If the MAC appears on a trunk port (e.g., Gi0/0), run the same commands on the downstream switch connected to that trunk port — the device is one hop further.

Time management: Candidates report spending 8–10 minutes on this PBQ unprepared. Practice in Packet Tracer until running these 4 commands and cross-referencing output takes under 3 minutes.

Exam strategy: Flag it, skip to MCQs, return with remaining time.

⚠ Exam Traps
  • show vlan only shows access ports — trunk ports don't appear in VLAN output
  • tracert * * * means ICMP is blocked at that hop, not necessarily that the hop is down
  • netstat -r shows routing table on a host (same as route print on Windows)
  • APIPA (169.254.x.x) = DHCP failure — not a bad IP address, a diagnostic signal
  • pathping is Windows only; combines ping + traceroute; shows per-hop loss statistics
  • show arp on a switch is only populated if the switch has SVIs (Layer 3 switch) or is a router
✓ Quick Recall
  • 4 discovery commands: show mac address-table, show arp, show vlan, show ip interface brief
  • MAC→Port: show mac address-table
  • IP→MAC: show arp
  • Port→VLAN: show vlan
  • APIPA 169.254.x.x = DHCP server unreachable
  • DNS name fails but IP works → DNS issue, not routing
  • ipconfig /flushdns clears DNS resolver cache
  • Routing loop → traceroute shows packets cycling between same hops

Rogue DHCP Server Scenario

Symptoms & Response

Symptom: Some clients receive wrong default gateway or wrong DNS server; internet stops working for affected machines; ipconfig /all shows unexpected gateway IP.

Cause: A rogue DHCP server (unauthorized device, misconfigured VM, or attacker device) is responding to DHCP Discover before the legitimate server.

Fix: Enable DHCP snooping on the switch — marks only specific trusted ports as allowed to send DHCP Offers/Acks. Untrusted ports that send DHCP Offers are shut down.

Locate rogue server: Check DHCP lease logs; use show ip dhcp snooping binding on the switch; trace MAC of rogue server to physical port.

ARP Poisoning Scenario

Symptoms & Response

Symptom: Legitimate users experience intermittent connectivity or certificate errors; attacker is intercepting traffic between victim and gateway.

Detect: arp -a on victim shows gateway IP mapped to an unexpected MAC address. Two hosts claim the same IP in ARP table.

Fix: Enable Dynamic ARP Inspection (DAI) — validates ARP packets against DHCP snooping binding table. Forged ARP replies are dropped.

TypeIndicatorMitigation

⚠ Exam Traps
  • DHCP snooping prevents rogue DHCP; DAI prevents ARP poisoning — these are different mitigations for different attacks
  • Certificate errors can indicate MITM — don't just click "proceed anyway" in a troubleshooting context
  • An ARP table with two entries sharing the same IP is a strong indicator of ARP spoofing — not always a misconfiguration
  • Containment (isolate the host) comes before eradication — never skip directly to reimaging without containing first
✓ Quick Recall
  • Rogue DHCP → DHCP snooping
  • ARP poisoning → Dynamic ARP Inspection (DAI)
  • Certificate error + traffic misdirection → suspect MITM
  • Unknown open port → check with netstat -an
  • APIPA + DHCP failure → check DHCP snooping isn't blocking legitimate server
  • Incident response order: Identify → Contain → Eradicate → Recover → Document
  • Duplicate IP in ARP table = ARP poisoning suspect, not just config error
